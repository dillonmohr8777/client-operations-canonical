03 · Chronology
Milestone 1 (Phase 1) · Discovery, Requirements and Architecture

The foundation: what Bridge is,
who it serves, and how it is built.

Milestone 1 turned an idea and a set of client-authored concepts into a documented product with named roles, an agreed MVP boundary, a technical architecture, and a compliance intake translated into product requirements. Status: delivered and paid. The technical plan and research findings were delivered on July 27 and the client's written response on August 5 was "the specs are awesome, the research is top tier" — warm, but not a formal milestone acceptance. No dated acceptance artifact was recorded, which is worth closing retrospectively.

What was researched and decided

  • The MVP boundary — what ships first and what is deliberately deferred
  • The contracted core user set: brands, retailers and dispensaries, sales representatives, and administrators
  • Priority journeys per role, and the low-fidelity flow direction validated before any visual polish
  • The ownership split between front-end delivery, UX, backend integration and final acceptance
  • A written exclusion list — algorithmic feed, advanced social graph, native mobile apps, recommendation engine, in-platform payments, subscriptions and marketplace ordering are all outside this build

The architecture put in place

  • Browser-based, role-based platform: Next.js, React and TypeScript on the front end
  • PostgreSQL with row-level security as the data and permission substrate
  • Git-linked continuous deployment to two hosted environments
  • A private source repository with an explicit branch model and review gate
  • An open decision register carrying every unresolved product question with a named owner and a decision-by point

The prototype families and the brand source

InputWhat it was and what it became

Compliance shaped the product, not just the paperwork

The verification and legal inputs were not filed away — they became structural. Three things in the live product exist because of them: the 21+ confirmation that blocks every route before entry, the two-mode profile that separates what the public sees from what verified businesses can access, and the admin queue that treats verification as a reviewable case with a status and a waiting time rather than a checkbox.

In progress. The front end is complete;

Steps 2 and 4 need a product decision from Melissa and Tori

Step 1 is deliberately the only step live in production. Steps 3 and 4 are not missing routes or a hosting problem — they need a real member identity, organization-scoped drafts, protected evidence storage and a review case, all of which are backend-owned. They also need a product answer on what verification evidence each of the twelve roles must supply and what the public "Verified" badge promises.

This has been stated plainly to the whole team, in writing, since August 31: Step 2 and Step 4 product approval is still with Melissa and Tori — do not represent those screens as client approved. That instruction still stands today, and this report holds to it.

One HTTP client, one contract

Registration, sign-in and sign-out were added to the same typed client every other call already uses — so they inherit one base URL, one status mapping (401 unauthenticated, 403 forbidden, 400/422 validation, 409 conflict) and one error type. A second, parallel HTTP client that had bypassed that contract was folded back in.

A mock fallback means sign-in and account creation work with no backend at all, which is what makes the flow reviewable today.

Session handling and role-aware routing

  • No token in browser storage — the session is read from the API on each load, as a cookie session requires. A test asserts no client file touches web storage
  • Sign-in sends members to their profile and administrators to the admin workspace
  • The return-path parameter accepts only same-origin paths; absolute URLs and protocol-relative hosts are rejected
  • Every routing rule carries an explicit note that client-side routing is presentation only and never authorization — the API must still enforce it
07 · Milestone 3
Milestone 3 · Quality, accessibility and continuous integration

Every required state, measured contrast,
and a build that now checks itself.

Required states across every route

One shared component now covers loading, empty, error, forbidden, unavailable and retry, with the correct assistive-technology roles and busy states. Error text is filtered: only a curated user-facing message is shown, so an internal error, a stack or a raw backend string can never reach the screen.

  • Sign-in never distinguishes "no such account" from "wrong password"
  • A permission denial offers no pointless retry; a service outage does
  • Explore shows a visible notice when browser storage is unavailable instead of failing silently
  • The admin queue has a real empty state with a reset action

Accessibility, measured not asserted

An automated check implements the published contrast formulas, reads the colour tokens directly out of the stylesheet so measured values can never drift from what ships, and asserts the AA threshold for every rendered text-on-background pair in all three themes.

  • Five contrast failures in the admin panel fixed — the worst was 2.88:1 against a 4.5:1 requirement
  • Two further failures found in the existing theme tokens that nobody knew about, including form error text at 2.22:1 — effectively unreadable — now 6.02:1
  • The keyboard skip link, previously hidden on admin pages, is present again
  • Sidebar controls given 44 px minimum touch targets; reduced-motion preference respected

Why continuous integration mattered here

The repository had no automated checks at all, which is how a branch with a failing test reached a pull request in the first place. Install, test, type-check, lint and build now run automatically on every pull request into the development and production branches. The build step deliberately pins the API origin empty, so each run proves the documented no-backend default still builds. Twenty-one new tests cover the twelve-role catalogue, the role round-trip from Step 1 to Step 2, post-sign-in landing paths, the open-redirect guard, the unified client, and the complete account-creation flow with no backend.

10 · Verified metrics
Integration · The contract handed to Greencubes

What the front end promises the backend,
and what is still outstanding.

Two documents were published on August 31 and handed over: an integration pipeline describing repository ownership, the branch and review model, hosting, access and the security rules; and an API contract naming every endpoint the front end already calls, with request and response shapes and the exact status mapping expected.

Delivered and independently verified

  • Server-side role enforcement that correctly rejects both missing and forged credentials on every protected route
  • A real cross-origin allowlist naming the exact production, preview and local origins, returning nothing for an unknown origin
  • Strong response security headers and a consistent error envelope
  • Working health and version endpoints
  • Registration, sign-in, password recovery and email re-verification screens
  • An admin verification queue sending filters as real server-side parameters

Outstanding before Milestone 3 can close

  • Six of the nine required session claims are absent — including the age-eligibility signal that the 21+ gate depends on, which today has no server-authoritative source
  • One missing response header currently prevents cookie sessions from working; it is the single root cause behind three separate defects
  • Access and refresh tokens are being written to browser storage, against the written security rule
  • No route table or response examples, so the front end defensively probes several possible response shapes
  • The verification-case contract — paginated cases, case detail, evidence references, decisions with reason codes and audit events
  • Backend repository, branch, commit and staging origin — the precondition set on August 31 for turning mock mode off
  • Storage rules: buckets, file types, size limits, signed URLs and retention

One approved screen was replaced and has been restored

The backend delivery removed the Join Step 1 role grid and replaced it with a sign-up card. That deleted the only place the product captures a member's role — which the organization onboarding and the verification flow both depend on — and removed the exact screen whose Step 2 and Step 4 product approval is still open with the client. Rather than reverting the work, both screens were kept: Step 1 remains the entry point unchanged, and account creation became its own Step 2. Nothing was lost on either side.

The security posture is the strongest part of the backend delivery

Real server-side role checks, a correct origin allowlist and strong headers are the hard parts and they are done properly. The outstanding items above are contract and documentation gaps, not architectural ones, and they are inexpensive to close.
