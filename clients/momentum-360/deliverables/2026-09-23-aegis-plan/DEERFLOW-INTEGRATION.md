## Pause, cancel, approve, tenant boundaries

- **Pause is not run cancellation.** POST /api/scheduled-tasks/{task_id}/pause cancels queued occurrences atomically, but returns conflict for launching/running work (backend/app/gateway/routers/scheduled_tasks.py:378-406; backend/AGENTS.md scheduled-task contract). Resume and manual trigger are separate endpoints at scheduled_tasks.py:409-457.
- **Active run cancellation exists separately.** POST /api/threads/{thread_id}/runs/{run_id}/cancel is permission-gated and routes to RunManager.cancel (backend/app/gateway/routers/thread_runs.py:1239-1297; manager implementation backend/packages/harness/deerflow/runtime/runs/manager.py:1309-1375). Command Center asks for confirmation before calling it (command-center.tsx:851-889). Cancel stops the DeerFlow run; it cannot undo a remote side effect already completed by a tool.
- **Durable approval is missing.** ask_clarification interrupts a run and renders a human input card (backend/packages/harness/deerflow/tools/builtins/clarification_tool.py:22-95; frontend interaction owner is frontend/src/components/workspace/messages/human-input-card.tsx). This is general user input, not an approval record bound to a specific external action, payload hash, expiry, actor, and one-time execution. No WordPress publish/update approval endpoint or awaiting_approval queue was found. Therefore do not make any WordPress mutation tool available in the initial stage; prose instructions or a clarification card are not an enforcement boundary.
- **Data boundary is account/user, with organization columns in active work.** The runtime contract says user_id remains the current boundary and projects/threads/runs/schedules/artifacts are user-owned; projects are organization containers, not team tenancy (plans/momentum-enterprise-runtime-contract.md:6-18). Scheduled task SQL derives organization_id from the authenticated user or verified owned thread (backend/packages/harness/deerflow/persistence/scheduled_tasks/sql.py:124-127; model field at .../scheduled_tasks/model.py:17). Creation schema has thread_id, context mode, assistant, title, prompt and schedule, but no project_id (scheduled_tasks.py:106-124). Use one dedicated NeedMomentum project and a verified project-associated thread; task ownership still comes from authenticated user and thread access, never a client-supplied project/org claim. Avoid treating the internal owner_user_id launch plumbing as team authorization: the runtime contract requires durable delegation before organization-scoped internal calls (plans/momentum-enterprise-runtime-contract.md:42-59).

## Smallest staged implementation

1. **Read-only watchdog:** create an owner-scoped scheduled task attached to a dedicated NeedMomentum project thread. Limit destinations to the canonical public site and explicitly approved read sources; emit one concise status/diff artifact, observed URL/time, and clear changed / unchanged / blocked status. Do not enable CMS credentials or mutation tools.
2. **Local draft executor:** add a second task (manual trigger first, then schedule only after receipts look right). It may generate copy, code or a deployable preview bundle in run outputs; require present_files and validate links/content before reporting complete. Use Command Center receipts and existing cancellation.
3. **Stage adapter, only if needed:** add the minimum isolated WordPress staging-only transport after confirming an isolated staging target and action allowlist. It must be unable to address production, send, spend, or publish; persist request/response hashes and a readback receipt, and make retries idempotent. Keep a clean path back to the staged artifact.
4. **Approval boundary before any CMS mutation:** introduce a durable, single-use approval record bound to owner, target site/environment, action, exact payload hash, expiry and approver; execution revalidates all fields server-side and rejects replay, changed payload, revoked access or production target. Do not treat chat wording, task prompt, or a UI-only button as approval enforcement. Production publish/send/spend remains separately gated.

## Risks and acceptance evidence

- A scheduled prompt is not a tool permission policy: any existing enabled browser/MCP/sandbox capability could exceed the intended destination or side effect. Validate the actual per-user enabled tool set before scheduling; keep the watchdog read-only and the draft executor disconnected from CMS writes.
- launch_scheduled_thread_run sets context.non_interactive=true (services.py:2107-2118); scheduled tasks cannot depend on clarification cards to ask for missing data. Missing sources or ambiguous diffs must produce a blocked artifact and stop.
- Reused-thread context can accumulate; choose either one controlled project thread with explicit checkpoint/context rules or fresh_thread_per_run with an explicit project-artifact retrieval input. Do not assume a fresh scheduled thread inherits project documents.
- Before stage: prove a synthetic scheduled occurrence follows queued → running → terminal, recovery does not duplicate it, its run and artifact are owner-scoped, pause cancels queued work, active run cancellation works through its guarded route, and a failed artifact presentation fails the delivery receipt.
- Before enabling WordPress staging: negative tests prove production hostname/path, publish/status transition, outbound message, arbitrary URL/SSRF, credential disclosure, changed payload, expired/replayed approval and cross-user task/thread/artifact access are rejected; positive test writes only to disposable staging and reads back the exact payload/hash.
- Docker remains the existing stack (Nginx, Gateway, Frontend, Redis; optional Kubernetes provisioner) in docker/docker-compose.yaml:29-211. Gateway hosts the runtime and durable state volume; there is no executor service to add. New Compose service/socket exposure would expand risk and is unnecessary for phases 1–2.
